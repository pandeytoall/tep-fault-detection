# Phase 2b design decisions (agreed with the user, 2026-10-25)

1. **Cases:** 25 from the testing family: one run per fault 1-20 plus 5 normal runs. Run IDs picked with seed 42, all distinct, so no case shares a noise stream with another case. Stored as `case_01`..`case_25`; the answer key is in a file the MCP server never reads. Full 48 h replayed; fault start not given to the assistant.
2. **Top contributing readings:** PCA only. Relative SPE and T² contributions per reading, averaged over the requested window (default: alarm window), divided by each reading's mean contribution on the 100 normal `limit` runs. Top 5 per statistic, with real names and units. Reconstruction-based contributions (RBC) are a phase 4 comparison.
3. **Scoring:** the assistant ends each case with a fixed block: `status` (fault / normal / can't tell), `unit` (feeds, reactor, condenser/separator, compressor/recycle, stripper), `idv` (up to 3, best first), `evidence`. Headline = unit accuracy on fault cases excluding 3/9/15. Strict = IDV top-1 and top-3. Normal cases correct only if "normal". Faults 3/9/15 reported separately; "can't tell" counts as honest there. IDV-to-unit table in the answer key, from Downs & Vogel, checked by the critic. Report counts, not just percentages.
4. **Plant notes:** four short notes in our own words, each citing its public source: (a) process description (Downs & Vogel 1993), (b) tag list of the 52 readings with names, units and plant unit (from the phase 1 variable map), (c) IDV 1-20 disturbance list, one line each, describing the disturbance only, (d) monitor guide (T², SPE, limits, relative contributions). No symptom tables (which readings a fault moves), from papers or from our results; those are for v3 RAG. The `researcher` drafts them; the orchestrator checks the no-symptoms rule.

## Critic review (opus, high): AGREE WITH CHANGES on 1-3, AGREE on 4. Changes adopted
- **Sandbox the assistant:** run it headless (`claude -p`) from an empty folder, with only the 4 MCP tools allowed (no file, shell or web tools). A fresh session per case. The prompt doesn't say how many cases are faulty or normal.
- **Historian holds only the case runs.** No `faultNumber` or `simulationRun` columns. Case numbers come in a seed-42 shuffled order. Each case's start is cropped by a random 0-80 samples (seed 42), so the fault doesn't always start at 8 h. The answer key and the case builder sit outside the assistant's reach.
- **Dev vs test:** prompt and tool iteration uses dev cases built from training-family `dev` runs. The test case set is frozen and reused unchanged for v1, v2 and v3, so versions compare case by case.
- **Contribution normalisation uses `fit` normal runs,** not `limit` (keeps the "limit = alarm limits only" rule). The T² contribution formula is written into the spec. When there's no alarm, the default window is the whole case. The normal mean has a floor, so ratios don't blow up.
- **Units:** the 8 plant units in `src/variables.py` map to the 5 scoring units. The mapping goes in the tag-list note and the answer key. IDV 16-20 are labelled "unknown unit": they're left out of the unit headline and scored on status, with IDV top-3 as background.
- **No-LLM baseline:** plant unit of the top SPE contributor, plus chance level.
- **Report** counts with 95% intervals. Log model ID, settings, prompt hash and tool version.
- **Monitor guide** contains no per-fault results. Known limit, stated in results and posts: Claude may remember TEP papers, which no note can control.
- **Cases and repeats (user, 2026-10-25): option B.** 3 testing runs per fault (60) + 10 normal = 70 test cases, 1 run each, plus 10 of them (seed 42) repeated 3 times. If fewer than 8 of 10 repeated cases give the same answer all 3 times, upgrade to 3 repeats for all cases (majority vote) for every version. Log tokens per session on dev cases first.
